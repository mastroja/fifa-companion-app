- [~] **Fix auto-refresh stealing window focus and pausing the game**. *(2026-09-13 — confirmed on Jake's machine that Live Editor has no window of its own; it draws as an overlay inside the game's own render, so there's no HWND to `FindWindow`/`PostMessage` against, ruling out the originally-sketched approach. First fix: `triggerLiveEditorRefresh()` in [main.js](main.js) was using `WScript.Shell.AppActivate` + `SendKeys`, which only delivers a keystroke to whatever window has OS focus, forcing the game to the foreground first — replaced with a `user32.dll` `keybd_event` call, a true OS-level synthetic keystroke needing no window activation. Also flipped auto-refresh to default ON and removed the stale `document.hasFocus()` gate in [index.html](index.html) that only let it fire while the companion app itself was focused.*
  - ***Bug found via live testing 2026-09-13: `keybd_event` doesn't actually work.*** *A real physical F10 press triggered the export; the app's injected `keybd_event` one didn't (confirmed by directly watching the export file's timestamp — it stayed frozen across the app's auto-refresh cycles and a manual PowerShell test, only moving when the user pressed F10 for real). Root cause: `keybd_event`/plain `SendInput` only inject at the OS message-queue/low-level-hook layer. A tool that renders its own in-game overlay (like Live Editor does) commonly reads input more directly (DirectInput/RawInput) instead, which only sees genuinely hardware-sourced key events and never observes a plain synthetic one.*
  - **Attempt 2 (2026-09-13): `SendInput` + `KEYEVENTF_SCANCODE`** (real hardware scan code, not just a virtual-key code) — also failed live testing. Same result: a real F10 press worked, the injected one didn't.
  - **Attempt 3 (2026-09-13): `PostMessage` of `WM_KEYDOWN`/`WM_KEYUP` straight to the game's own window handle** (no `AppActivate`, no focus touch at all) — also failed. Confirmed directly by watching Live Editor's own Lua log while clicking Refresh: nothing happens for any of the three synthetic approaches, but a real physical F10 press shows up in the log immediately.
  - **Conclusion:** Live Editor almost certainly uses a system-wide low-level keyboard hook to catch its hotkey regardless of what's focused — the standard way to implement a "global hotkey that works no matter what's focused" — and such hooks routinely filter out anything flagged as synthetic/injected, which `keybd_event`, `SendInput`, and `PostMessage` all are by construction. There's no flag or delivery method left to try in software; a synthetic keystroke that's invisible to focus AND accepted as genuine isn't achievable without a virtual input driver (a much bigger step, out of scope for now). The only approach ever confirmed to work is the original `AppActivate` + `SendKeys` — which requires the game to be the genuine foreground window at the moment F10 fires, full stop.
  - **Final fix (2026-09-13), reframed per the user's own read on the real requirement:** the "steals focus" problem only actually matters for auto-refresh (which needs to run invisibly while the user is playing) — clicking the Refresh button already means the user left the game to interact with this app, so activating the game there isn't a new problem, it's the button's original, always-accepted behavior. `triggerLiveEditorRefresh(isManual)` now branches on that: `isManual` (button clicks) always proceeds with `AppActivate` + `SendKeys` as before; auto-refresh ticks check whether the game is *already* the foreground window first (via `GetForegroundWindow`/`GetWindowText`) — if yes, `AppActivate` is a genuine no-op (no focus-loss/gain cycle, nothing visibly changes) so it's safe to proceed; if no, that tick is skipped entirely (tries again next interval) rather than forcing a switch. Threaded the `isManual` flag through `preload.js`/IPC and `index.html`'s `triggerRefresh()` (defaults to `true` for the button's existing zero-arg calls, `false` passed explicitly from the auto-refresh interval). Verified the generated PowerShell's conditional logic evaluates correctly for both branches by extracting and running the real function in isolation. **The one gap this doesn't cover:** auto-refresh while the user is tabbed away from the game (e.g., alt-tabbed to browse something) simply waits until they tab back — an accepted tradeoff given the alternative is forcing an unwanted switch. Needs live in-game re-test.

- [x] **Open question: is the 1-minute auto-refresh interval appropriate?** *(Resolved 2026-09-13 — keep it at 60s. A single F10 run writes ~400KB across 6 export files (squad 58KB, calendar 85KB, league stats 156KB, transfers 90KB, youth 1.3KB, watchlist 11KB) and [export_all.lua](assets/export_all.lua) iterates league-wide team stats and transfer records, not just the user's team — that's negligible disk I/O and Electron-side parse/SQLite-upsert cost regardless of interval, so "computing resources" was never really the constraint. The actual cost is the Lua export running synchronously inside the game's own process, which likely costs a fixed frame-hitch each time it fires; going faster than 60s would just pay that hitch more often for data (squad/transfers/standings) that doesn't change second-to-second, with no real upside — even the stat-diffing feature below wouldn't meaningfully benefit given its own attribution ambiguity at any interval. Decided to leave at 60s, only revisiting downward (90-120s) if live testing shows a perceptible in-game stutter each time it fires.)*

- [x] **Simulated match stats via stat-diffing during live fixtures**. *(Done 2026-09-13 — confirmed end-to-end: real rows now exist in `match_events`, the Refresh mechanism works reliably (focus-aware `AppActivate`+`SendKeys`), and the inline UI on both Home and Calendar displays them correctly, including manual edits, own goals, and penalties.)* The game doesn't expose per-match stats directly. Workaround: the app already knows which fixture is currently being played (by date/schedule); each sync, snapshot player goals/assists and diff against the previous sync. If a player's goal count increases while today's fixture is live, record it as a goal in that fixture; if an assist stat increases in the same sync as a goal, infer the goal was assisted by that player. Not every goal has a paired assist (solo efforts, penalties, own goals) — handled as goals with no assist rather than errors.
  - Effectively uses the sync cadence as a flip-book/diffing mechanism to reconstruct match events (goals, who scored, who assisted) without the game natively exposing them.
  - **Known limitation:** only works for **played** matches where a sync happens to land while the goal occurs — not **simulated** matches (no live polling window during a sim), and not matches missed entirely while the app was closed.

## Carried forward from v1.6.0 (unfinished)

- [ ] **Awards tracking** — MOTM, POTM, POTS, Ballon d'Or. *(Under active investigation as of 2026-09-12 — reassessed, easier than first thought for MOTM/POTM:*
  - *Live Editor does expose a real per-competition-per-season `motm` (Man of the Match count) field, confirmed in its bundled `export_season_stats.lua` reference script and `DOC.MD` — same data category as goals/assists/yellow/red the app already imports. Docs flag it `(not sure if data is correct)`, so spot-check a known player's count before relying on it.*
  - *That field alone only supports a season-total "Most MOTM awards" honor (same pattern as existing Golden Boot/Playmaker/Golden Glove) — it has no date/match attached, so it can't directly give month-by-month POTM.*
  - *Proposed workaround for monthly POTM (diff-based, needs no new Live Editor data): store each player's MOTM count on every refresh/import, and when it increases, attribute the award to the most recent match(es) played since the last refresh (dates already available from calendar/match data). Rule of thumb floated: 2+ MOTM in a month = Player of the Month. Works cleanly when refreshing close to game time (the common case, especially with auto-refresh). Edge case resolved: if the user sims many days/weeks without refreshing and a count jump can't be pinned to a single month, just skip assigning POTM for that stretch rather than guessing — no award is better than a wrong one.*
  - *POTS/Ballon d'Or (real-world awards) — still being searched for an in-game source (world player of the year / league player of the year exist in-game per the user). If none is found, manual entry via the existing `world_league_awards` pattern is the fallback.*
  - *No per-match player data exists anywhere else (see Per-game stats below) — the MOTM diffing approach above is the one path that sidesteps that gap.*
  - **Sub-task: build our own Player of the Year value, if not tracked in-game.** Composite score from season-cumulative stats: # of MOTM, # of goals, # of assists, # of clean sheets (GKs/Defenders/CDMs only), average match rating. **POTM deliberately excluded** — it's arithmetically derived from MOTM (2+ MOTM in a month), so including both would double-count the same underlying signal; MOTM alone represents it.
    - *Design goal, 2026-09-12: these awards naturally skew toward attacking players (goals/assists only exist for them), so the formula should be built to still give defensive/midfield players a real chance rather than locking POTY to strikers by default.*
    - **Final weights, locked in 2026-09-12: MOTM 30% / Average rating 30% / Goals+Assists 25% / Clean sheet rate 15%.** Revised up from an initial 40/20/25/15 rating-heavy split after testing against made-up sample data showed match ratings cluster too tightly across players (e.g. 7.3–7.9) to meaningfully separate a season's best from the rest — MOTM and G+A vary more and do more actual differentiating work. Bumping MOTM specifically (rather than G+A) to reach parity with rating was chosen deliberately because MOTM is a stat every position can earn, unlike goals/assists — validated against the sample data below, where the goalkeeper's rank rose from last-place-adjacent up to mid-table once MOTM carried equal weight to rating.
    - *Normalizing counting stats (MOTM/goals/assists/clean sheets) by appearances or per-90 rather than using raw totals is the key lever for fairness across positions — raw counts alone would still hand it to whichever attacker played every match.*
    - *Scoring mechanics: each component is converted to a fixed 0–100 scale (not relative to the season's field, so scores stay comparable year to year) before weighting: rating → `(rating/10) × weight`; MOTM → `min(MOTM/Apps ÷ 0.5, 1) × weight` (50% MOTM rate = ceiling); Goals+Assists → `min((G+A)/Apps ÷ 1.0, 1) × weight` (1 contribution/game = ceiling); Clean sheets → `(CS/Apps) × weight`, 0 for non-GK/DEF/CDM. Sum of all four = final 0–100 POTY score.*
    - *Validated 2026-09-12 against a made-up 10-player/38-game sample (3 ST, 3 W, 2 CM, 1 RB, 1 GK): 2 players failed the 70% appearance gate and were excluded; of the 8 eligible, final ranking was Striker (62.0) > Winger (56.1) > Striker (49.4) > Winger (48.6) > Goalkeeper (46.6) > Center Mid (46.3) > Right Back (44.4) > Center Mid (40.1) — the striker still wins (deservedly, on a 28-goal season), but the goalkeeper landing above a center mid confirms the formula gives non-attacking positions a real shot rather than being structurally locked out.*
    - **Eligibility gate, decided 2026-09-12: minimum 70% of the season's matches appeared in to qualify for POTY.** Needed because rate-based normalization (above) is blind to sample size — without a threshold, a player with a handful of appearances and a flawless rate could outscore a full-season starter. Below 70% appearances, a player isn't considered for POTY regardless of composite score.*
